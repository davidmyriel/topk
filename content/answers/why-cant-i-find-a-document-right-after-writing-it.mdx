---
title: "Why can't I find a document right after writing it?"
description: "Eventually consistent search makes tests flaky and users confused. TopK returns a sequence number on every write that your next query can wait for."
---

## Short answer

Every write returns an LSN. Pass it to the next query. The query waits until that write is visible.

```python
lsn = client.collection("notes").upsert([
    {"_id": "n1", "text": "Call the dentist"}
])

results = client.collection("notes").query(
    select("text").filter(match("dentist")).limit(5),
    lsn=lsn,
)
```

No sleep loops. No polling.

## The problem

You upsert, you search, nothing comes back. Seconds later it works.

- Pinecone closed the report as won't-fix. Serverless indexes are eventually consistent ([pinecone-ts-client #226](https://github.com/pinecone-io/pinecone-ts-client/issues/226)). Forum users report 2 to 3 minutes.
- Milvus has dozens of consistency issues, including strong consistency returning empty results ([#16949](https://github.com/milvus-io/milvus/issues/16949)).
- Elasticsearch refreshes every second by default. "Document not found immediately after save" is a yearly thread.

Where it bites:

- Integration tests need retries.
- A user uploads a file and searches for it. Empty.
- An agent writes a memory and reads it back in the same turn. Gone.

## How TopK handles it

Writes go to a write-ahead log with a log sequence number. A query given that LSN is rejected until the read path has caught up, and the SDK retries automatically.

Three consistency levels are available per query:

| Level | Behavior |
|---|---|
| `indexed` | Fastest. Only fully indexed data. |
| `balanced` | Default. |
| `strong` | Waits for all writes. |

Combine an LSN with `strong` for read-your-writes:

```python
results = client.collection("notes").query(
    select("text").filter(match("dentist")).limit(5),
    lsn=lsn,
    consistency="strong",
)
```

From SQL:

```sql
SET consistency_level = 'strong';
SELECT text FROM notes WHERE match('dentist') LIMIT 5;
```

From the Elasticsearch-compatible API, use `?refresh=wait_for` on writes.

## Trade-off

Waiting for an LSN adds latency when the write is very recent. Typical write-to-queryable is under a second in balanced mode. Use LSNs where correctness matters and defaults elsewhere.
