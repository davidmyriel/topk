---
title: "How do I keep each customer's data separate without creating thousands of collections?"
description: "One collection, one partition per tenant. No per-collection memory cost, no collection cap, atomic tenant delete."
---

## Short answer

Pass the tenant ID as the partition name. Partitions are created on first write, fully isolated, and cost nothing when idle.

```python
client.collection("docs", "acme-corp").upsert([
    {"_id": "d1", "title": "Q3 report", "body": "..."},
])

client.collection("docs", "acme-corp").query(
    select("title").filter(match("report")).limit(10)
)
```

## The problem

You have a SaaS product. Customer A must never see customer B's documents. The obvious answer is one collection per customer.

That breaks at scale:

- Qdrant users hit out-of-memory at 5,000 per-user collections ([#5032](https://github.com/qdrant/qdrant/issues/5032)). Empty collections still consume RAM. Maintainers advise against many collections.
- Milvus caps at 65,536 collections and warns that thousands slow the server.
- Weaviate's own issue says many classes "does not scale well" ([#2970](https://github.com/weaviate/weaviate/issues/2970)).
- Elasticsearch limits shards per node to 1,000. Index-per-tenant hits it fast.

The alternative, a `tenant_id` filter on one big collection, runs into the [filtered-search problem](/answers/why-does-filtered-vector-search-return-fewer-results) and shares one index across every customer.

## How TopK handles it

A partition is a physically separate slice of a collection with its own indexes. Reads and writes scale with the number of partitions. A dormant tenant lives on object storage only.

Same schema, same query features, same SDK. Only the partition name changes.

```python
tenant = request.user.org_id

client.collection("docs", tenant).query(
    select(
        "title",
        score=fn.semantic_similarity("body", query_text),
    )
    .sort(field("score"), asc=False)
    .limit(10)
)
```

List and delete tenants:

```python
for p in client.collection("docs").list_partitions(prefix="acme-"):
    print(p.name)

# removes every document for the tenant atomically
client.collection("docs").delete_partition("acme-corp")
```

From SQL:

```sql
SELECT title FROM docs$acme_corp WHERE match('report') LIMIT 10;
DELETE FROM docs$acme_corp;
```

## Limits

- 1 billion documents per partition.
- Write throughput is per partition, so heavy tenants do not slow light ones.
- Cross-tenant queries need a separate shared collection, by design.
