title: "Why does building my vector index take hours, and why do I have to babysit it?"
description: "HNSW builds are single-threaded, memory-bound, and restart from zero. TopK indexes on write and compacts in the background. There is no build step."
---

## Short answer

TopK has no `CREATE INDEX` step. Indexes are declared in the schema, maintained on every write, and compacted by a distributed background service. You never rebuild.

```python
from topk_sdk.schema import text, f32_vector, vector_index, keyword_index

client.collections().create("docs", schema={
    "title": text().required().index(keyword_index()),
    "embedding": f32_vector(dimension=1024).required().index(vector_index(metric="cosine")),
})
# Start writing. Documents are queryable in under a second.
```

## The problem

- pgvector: HNSW on 10 million vectors took more than 24 hours on 4 CPUs ([#300](https://github.com/pgvector/pgvector/issues/300)). A build on tens of millions was stuck at 29 percent after 19 hours with 40 GB of `maintenance_work_mem` ([#822](https://github.com/pgvector/pgvector/issues/822)). Parallel builds are still a top request ([#409](https://github.com/pgvector/pgvector/issues/409), [#500](https://github.com/pgvector/pgvector/issues/500)).
- After the index exists, inserts crawl. One report went from 20 rows per second to 3 ([#810](https://github.com/pgvector/pgvector/issues/810)).
- Weaviate users have asked for a reindex API since 2022 ([#2359](https://github.com/weaviate/weaviate/issues/2359), 70 reactions). Restarting a node reloads HNSW for "dozens of minutes" ([#7189](https://github.com/weaviate/weaviate/issues/7189)).
- Qdrant's optimizer can loop forever ([#8885](https://github.com/qdrant/qdrant/issues/8885)) and search quality degrades until a rebuild ([#7147](https://github.com/qdrant/qdrant/issues/7147)).

## How TopK handles it

Per the [architecture](/architecture) page, writes land in a write-ahead log on object storage and are queryable at balanced consistency in roughly 750 ms at p99. A compactor merges log entries into read-optimized segments across many nodes in parallel. Old segments are replaced, never rebuilt in place.

Practical effects:

- Bulk load at up to about 70 MB/s or 30k vectors per second per partition. Use more partitions for more throughput.
- Write speed does not drop after the index "exists" because there is no separate index lifecycle.
- Changing a field's index means creating a new collection and reloading, same as any schema change. There is no in-place reindex, and none is needed for normal operation.
