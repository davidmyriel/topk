title: "Why does my vector database need so much RAM, and how do I stop paying for it?"
description: "HNSW indexes must live in memory, so your bill scales with data you rarely query. TopK keeps everything on object storage and caches only what is hot."
---

## Short answer

Most vector engines keep the whole index in RAM because HNSW graph traversal does random reads. TopK stores all data on object storage and uses NVMe and RAM as a cache. Idle data costs storage only.

Nothing changes in your code. It is the same collection, same query API.

## The problem

- Milvus has over 130 issues with "OOM" in the title. One user saw memory reach 329 GB for 200 million vectors ([#40270](https://github.com/milvus-io/milvus/issues/40270)).
- Chroma: "Size of database cannot grow larger than available RAM?" has been open since 2023 ([#1323](https://github.com/chroma-core/chroma/issues/1323)).
- LanceDB ran out of memory creating an index ([#767](https://github.com/lancedb/lancedb/issues/767), 25 comments). Another user hit OOM on 180 million rows with 128 GB RAM.
- Qdrant reports high RAM even with `on_disk: true` ([#6077](https://github.com/qdrant/qdrant/issues/6077)).
- Elasticsearch's own sizing rule is `num_vectors * 4 * (dims + 32)` bytes of page cache ([#93670](https://github.com/elastic/elasticsearch/issues/93670)). Elastic shipped DiskBBQ in 2025 because HNSW "requires all vectors to reside in memory".

A billion 1536-dimension float vectors is roughly 6 TB. Nobody wants to rent that much RAM for data that is mostly cold.

## How TopK handles it

From the [architecture](/architecture) page:

- Object storage is the only durable store. A write-ahead log and LSM-style compaction keep it queryable.
- Executor nodes cache hot data in memory and on local NVMe. They are stateless and can be replaced.
- Read and write node pools are separate, so ingestion never competes with queries for memory.
- The `.bob` columnar format supports zero-copy reads of compressed vectors straight from storage.

What this means for you:

- Store a billion documents in one partition ([limits](/limits)).
- Quantize to f16, f8, u8, or binary to shrink further, with hamming distance for binary.
- Pay object-storage rates for data nobody is searching.

```python
from topk_sdk.schema import text, f16_vector, vector_index

client.collections().create("archive", schema={
    "title": text().required(),
    "embedding": f16_vector(dimension=1536).required().index(vector_index(metric="cosine")),
})
```

## Trade-off

The first query against cold data pays an object-storage read. After that it is cached. Latency targets in the [vector search guide](/guides/vector-search) are for warm data. Benchmark your own cold-start pattern before committing to a latency SLA.
