TopK plugs into the tools teams already use to parse, chunk, and retrieve complex documents. Every integration below uses the same engine, so each one gets:

- **Server-side embedding.** Add [`semantic_index()`](/guides/semantic-search) to a field and TopK embeds both documents and queries. You don't run an embedding model or keep model versions in sync between ingestion and query time.
- **Multi-vector retrieval by default.** `semantic_index()` runs on [topk-embed-v1](https://www.topk.io/blog/topk-embed-v1), a late-interaction model that keeps one embedding per token and scores with [MaxSim](/guides/multi-vector-search#maxsim-scoring). Token-level matching holds up on long documents, specific clauses, tables, and identifiers, which are the parts of a parsed PDF that single-vector embeddings tend to blur.
- **True hybrid search in one query.** A `semantic_index()` field also supports BM25, so semantic similarity, keyword score, metadata filters, and a custom ranking expression all run in [one request](/guides/true-hybrid-search). There's no second keyword index and no client-side fusion.
- **Visual documents.** An [`image()`](/sdk/topk-py/schema#image) field can carry a `semantic_index()`, so page renders, figures, and charts are searchable next to the text extracted from them.
- **Object-storage economics.** TopK separates compute from storage, so large document corpora cost a fraction of what memory-resident vector databases charge. See [Architecture](/architecture).
